## 2. ADR 0022 classification and exact identity gate

**Recommendation: option 2 — clarify/amend ADR 0022 before C2.** Distinguish:

| Category | Identity and compatibility authority | Activation |
| --- | --- | --- |
| **A: process-local RPC/live projection** (`ping`, advertised capabilities, event/listener or RPC reads) | In-process producer capability matrix, scoped to the active Pi session. | Keep ADR 0022's same-session `ping` and recognized protocol-v1/per-capability schema gate unchanged. |
| **B: filesystem enrichment** of an already-proven C1 `AgentRun` via `asyncDir` explicitly published in that run's persisted Pi tool result | Exact persisted result/producer IDs plus documented, versioned, bounded artifact at that reference. No RPC capability activated; no discovery, listener, polling, or historical authority. | **Separate exact reference/run/session/version gate**; no RPC ping. Current-view, optional, fail-closed enrichment only. |

**Literal reading:** yes, ADR 0022's Decision says *“any future live consumer must validate `ping` for the same Pi session before activating a capability”* and *“only the recognized RPC protocol v1 contract is eligible for future live enrichment.”* Its Consequences reiterate that. Mutable current-session B is plausibly “live consumption”; existing text does **not** exempt it. Do not silently implement B under unchanged ADR. **Likely intent:** the v1 `ping` rule protects live process-local producer capability activation; ADR's separate historical-authority rule already permits reading explicitly published references (the existing archive reader does so). Applying an RPC capability handshake to a documented file path is broader than needed for that boundary. Make this interpretation an explicit ADR amendment; this local note is not the amendment.

**Independent same-session/exact-run binding is possible, but stronger than earlier notes specified.** Required chain for B:

1. Read parent Pi JSONL for the **current session file**. C1 already requires a joined `subagent` call and successful matching tool result, `details.mode === "single"`, `results: []`, bounded raw `runId`, and `asyncId === runId` ([C1 `readAsyncLaunchRunId`](../../src/integrations/subagents.ts)); that persisted *same result* must publish bounded, absolute `asyncDir`. This proves the Inspector C1 launch observation before any artifact read. On conflicting references for one ID, skip; no new AgentRun, alias, parent, ID, or timestamp from file.
2. Read only its documented `status.json`. Require **exact** `lifecycleArtifactVersion === 3`, `mode === "single"`, root `runId ===` that validated raw launch ID, exactly one step, and **a present `sessionId` exactly equal to the Pi session file path containing the persisted publication**. Fail closed if session file unavailable, status session ID absent, or strings differ. The earlier proposal's *“check optional sessionId if present against Inspector parent session ID”* is insufficient and ordinarily wrong: [producer `resolveCurrentSessionId`](https://github.com/nicobailon/pi-subagents/blob/4af5e85a427b9f87334585ae8d0eb365d4dd2a1e/src/shared/session-identity.ts) chooses `sessionManager.getSessionFile() ?? getSessionId()`; [extension](https://github.com/nicobailon/pi-subagents/blob/4af5e85a427b9f87334585ae8d0eb365d4dd2a1e/src/extension/index.ts#L960-L971) uses this as `currentSessionId`; launcher passes it as runner `sessionId`; runner serializes `config.sessionId` into status. Inspector's `readSessionId()` instead calls `getSessionId()` (session UUID). A bare UUID comparison to status `sessionId` will fail on file-backed sessions. The current loader already has `sessionFile`; use that exact path, not a basename, directory, public digest, or inferred metadata. This contractual present-value requirement narrows the optional TS type deliberately; unsupported/fallback-only sessions get **no enrichment**.
3. Treat the producer as cooperative same-user evidence, not cryptographic attestation. Published paths and status may be replaced by a local attacker with filesystem write access; a ping also does not authenticate immutable file contents. Bound path/bytes, reject directory **and** final-file symlinks if promising no symlink traversal, no-follow/open/check the file, discard raw path/IDs/errors; failures preserve C1. Status can race, undercount, or disappear; never use it for history, status authority, billing, or completeness.

**What ping adds for B:** it proves the live RPC producer at that moment recognizes the parent session and advertises a compatible *RPC capability*. It does **not** establish that a separately read `status.json` is the same artifact/run or is fresh/unchanged, and cannot replace exact persisted-reference/artifact checks. Requiring RPC for B adds unnecessary process-liveness and protocol-v1 coupling: it would disable valid file enrichment during restarts/unavailable RPC despite an exact persisted reference, and expand a file-only C2 into an RPC integration. Keep A gated by ping; gate B independently as above. If the required `sessionId` equality cannot be satisfied on a particular run, **skip B** rather than relaxing this condition or switching to option 1 covertly.

## 3. Rechecked candidates on **published 0.71.0**

- **`toolCalls`: approved, narrowly.** [Tagged `subagent-runner.ts`](https://github.com/nicobailon/pi-subagents/blob/4af5e85a427b9f87334585ae8d0eb365d4dd2a1e/src/runs/background/subagent-runner.ts#L2988-L3004) increments *that single step's* `toolCount` by one on each child `tool_execution_start` with a tool name; root `toolCount` increments too but is aggregate for multi-step modes, so use **only** `steps[0].toolCount` after single-run/cardinality validation. It counts starts, not completed/successful tools, not native Inspector session tool calls; a failed/unfinished tool can count. Initial pending step omits the property; absence is **unavailable**, not zero. Explicit bounded integer `0` is a valid snapshot value, not proof that a completed run executed zero tools. Running status writes are coalesced (100 ms) and artifact reads race execution; an incomplete/running snapshot can undercount later or even already-started unflushed tool calls. Accept only as **partial/provisional current-view effort**, fill only absent C1 `AgentRun.toolCalls`, never replace persisted effort or present it as a final history count. Preserve C1 status/usage/accounting.
- **`model`: approved only for a completed step as a *settled, producer-reported label*, NOT an actually executed model.** `requestedModel` is launch intent before normalization ([published docs](https://github.com/nicobailon/pi-subagents/blob/4af5e85a427b9f87334585ae8d0eb365d4dd2a1e/docs/observability.md#status-and-result-fields)). The launcher's initial pending `steps[0].model` comes from the earlier `primaryModel`/thinking resolution, while it separately resolves `selectedModel` for the runner; they can differ ([tagged `async-execution.ts`](https://github.com/nicobailon/pi-subagents/blob/4af5e85a427b9f87334585ae8d0eb365d4dd2a1e/src/runs/background/async-execution.ts#L1832-L1893)). During running, `onAttemptStart` writes the attempted model, before a provider call; retries can change it. After a single step returns normally, the runner overwrites its field with `singleResult.model` and sets the step status (`:4659` and nearby); `singleResult` prefers attempted `candidate` to the child session's reported `run.model` and can retain a model even if no provider call occurred (`:1097`, `:1338`, `:1525`). **Merely requiring a terminal step status is not sufficient:** stop/failure paths can mark a step `stopped`/`failed` directly without that settled model overwrite (`:2294-2307`, `:4440-4470`). The source supports a narrower unambiguous gate: one step with `status === "complete"` (set on the normal returned-result path); omit model for pending/running/failed/paused/stopped/partial or any other state. Even `complete` does **not** prove a provider generation occurred. Existing Inspector [`AgentRun.model`](../../src/core/events.ts) means “bounded model label,” populated from the producer's persisted `SingleResult.model` when such a supported row exists ([`toAgentRun`](../../src/integrations/subagents.ts)), not measured provider usage. A completed step's reported model matches *that limited field meaning*; preselected/attempted model does not. Fill absent field only; keep persisted value first. If desired semantics are “model actually executed,” **do not approve model**: neither this artifact nor existing `AgentRun.model` proves it. Do not read `requestedModel` into this field.
