# M8.6 browser and chart baseline

Measured 2026-09-15 on `node v22.22.1`, `linux-x64`, against the browser asset
with SHA-256
`c0d68868d6451a89454ef2b7bf98ae3a32f56e51a9d837b7e65c3e5f9768c843` — the bundle
is deterministic, so that hash names exactly the bytes measured here.
Reproduce with `npm run benchmark:browser:release` (`5` warmups, `40` samples;
the raw artifact is written to `benchmark/artifacts/browser-latest.json` and is
not committed). The accepted baseline is `benchmark/baselines/browser.json`,
checked by `npm run benchmark:browser:check`.

Regenerate the baseline only when a retune is accepted:

```bash
node --import tsx benchmark/browser.ts --mode=release --write-baseline
```

These are measurements, not release gates. The baseline check fails on a
deterministic asset change (bytes, gzip bytes, or SHA-256) or on a wall-time
median beyond `2.5×` its recorded value; hard performance gates still begin only
after two accepted release baselines establish variance.

Notes for a future reader:

- The fixture is `tests/fixtures/bundles/inspector-bundle.json`, projected by L2
  exactly as the API returns it, so the chart draws two daily rows.
- Startup includes drawing the chart: the harness serves the real bundle and the
  real adapter, which is why this number is larger than the pre-chart `2.48 ms`
  recorded in `docs/roadmap.md` (that value came from a different local harness;
  the roadmap table states which harness measured each row).
- Chart update measures the path the application uses (theme recolor and
  redraw); a data change re-creates the chart from a new DTO, which is the
  chart-create number.
- `benchmark/run.ts` covers the corpus/analyzer/report path; this record covers
  the browser asset. Server startup/refresh stays with the release packaging job
  (Pre-M8.7).
